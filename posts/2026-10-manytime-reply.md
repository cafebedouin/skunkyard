Prepared with Claude Code (Anthropic, Claude Fable 5.1; review seats on Claude Opus 5.5, Grok and Gemini) for cafebedouin using peeryard v0.1.0 (ba56b25) on ergo 6.0.6 (devnet, one mining node), a public ergo 6.0.1 testnet node, sigma-state 6.0.7 for the driver, Fleet for the testnet funding, and a scan of a stopped mainnet node's history store; reviewed in two rounds before posting (`posts/REVIEW-manytime-reply.md`).

A hash-based lock (WOTS, n = 32, w = 16) that one key set spends many times, with the chain refusing a reused or lower leaf for everything the key set owns, runs on today's node with no fork: on a devnet and on public testnet, as a prototype, not something to use yet. Section 5 above listed this construction as unimplemented. Details, numbers and limits follow; nothing is asked of holders.

**The construction.** Two scripts. The singleton: one box per key set, marked by a token of supply 1 minted once, whose script commits to 16 WOTS keys as the AVL digest of their commitments (33 bytes at any count; the count is a script constant too) and carries the key set's index in R4. A spend names a leaf at or above the index, supplies that leaf's signature and lookup proof, and must recreate the singleton with the token and an index above the leaf it used; on the last leaf the token may move to a new key set's singleton instead. The deposit script, 61 bytes: a box here is spendable only in a transaction that also spends the singleton. The deposit address is the one a holder gives out; a plain payment to it is a usable deposit, and it does not change when the key set rotates. The signed message covers every input id and every output, so a deposit cannot be added to or removed from a signed transaction. The verifier is section 2's, reading the commitment from the tree; the index and token checks sit on the left of the `&&` and fail before any hashing. An earlier version kept the index in each box; the review seats found that a fresh deposit at the same address then started at 0 and would accept a leaf another box had used, which is why the counter moved into one box.

**Executed, on public testnet** (through a public testnet node, ergo 6.0.1, block version 4; the project's testnet wallet minted the token and funded the singleton, two plain deposits and one plain box at the singleton's own address, all in one transaction). Rejected by the node, with script costs in units: a forged signature, 37,915; a spend that does not advance the index, 73; a deposit spent without the singleton, 7; a transaction signed over the singleton alone and posted with a deposit added, 37,997; the plain box at the singleton's address, which has no token, with a valid signature, 23; leaf 0 signed again after the index read 1, 46. Confirmed: leaf 0 sweeping the first deposit (transaction `1ccc214b…`, index to 1), then leaf 3 sweeping the second (`f08692435…`, index to 4, the token carried both times, both deposits gone from the UTXO set). The devnet (ergo 6.0.6, block version 4) gave the same eight verdicts with the same rejection costs except the two that include a hash count (37,904 and 37,602). The hybrid `proveDlog(owner) && (this lock)` ran only under the earlier per-box version: the hash-only spend without the curve proof rejected, both proofs confirmed, 196 to 565 units and 95 bytes (56 of proof, 39 of the larger box) over the plain form.

**Numbers, per spend with one deposit** (derived from the printed figures). Script cost 37,762 to 38,204 units across the four valid spends, of which the deposit's script is 11; the one-time box in section 2 measured 37,592. 3,644 bytes against 2,345, because the 1,104-byte singleton rides along with the signature and proof. Per mainnet block about 148 by cost (8,001,091 ÷ (38,204 + 15,708 for two inputs and three outputs)) and 349 by size (1,271,009 ÷ 3,644), against section 3's 154 and 542. Rent: the singleton persists, about 1.38 ERG per four years at the current factor (1,104 bytes × 1,250,000 nanoERG), its clock restarting whenever the wallet sets the recreated box's creation height to the current one, as this driver does; a deposit is 102 bytes.

**What the chain enforces, and what it does not.** For the key set: the index never moves backwards, a leaf below it cannot spend, and nothing at the deposit address moves without the singleton; so a wallet restored from an old backup that signs a leaf the index has passed gets a rejection, on a deposit as on the singleton. What the chain cannot see is a signature that never reaches it: a signer who signs the current leaf twice off chain, or a replacement signed with leaf k + 1 while the original spend with leaf k then confirms, leaving k + 1 disclosed and the index at k + 1. Two public signatures from one leaf are the forgery window. The wallet therefore keeps one counter per key set, never decremented, and a wallet rebuilt from the chain skips ahead past the index by a margin, which the "at or above" rule allows at the cost of the skipped leaves. The singleton is the wallet's own box; if it writes an index at or past the leaf count the box is unspendable. Not shown: hiding which leaf signed (the register and the proof name it; the proof's sibling hashes reveal nothing about unused leaves by preimage resistance, with no domain separation, as section 2 noted); heights above 4, several deposits in one spend, the last-leaf rotation branch and the hybrid under this version (not run); a bad lookup proof at a legal index (by reading, still an exception rather than a false).

**Prior work.** QRL has enforced one-time use of XMSS indices at consensus since its XMSS addresses (2018), with a per-address bitfield over the first 8,192 indices; the singleton is that bitfield's UTXO form, with the difference that a lower bound in a register burns a skipped leaf where a bitfield would keep it. WOTS-Tree (Mateos, ePrint 2026/374) brings XMSS to Bitcoin with up to 2^21 leaves and recovers the index by scanning the chain, the signer enforcing it; Kudinov and Nick (2025/2203) prefer stateless schemes for Bitcoin because of the state-rollback failure, while keeping the stateful option open; BPQS (2018/658) chains two-leaf trees with signer-side state. On account chains, the Solana Winternitz vault (2025) has a program verify one WOTS signature and move the funds to a vault under the next key, and Ethereum contract wallets rotate a stored key hash per transaction. What is added here is a many-time counter enforced by a box script on a UTXO chain whose protocol knows nothing about the scheme, with a fixed deposit address. The search scope is in the repository's prior-art note; it did not cover the Bitcoin mailing lists or IOTA.

**How many leaves.** Over 791,286 mainnet blocks (789,437 contiguous from genesis plus 1,849 near the tip; the 2019 to 2022 era, 42% of today's height), 263,160 P2PK keys signed at least one input; by inputs signed, which is leaves consumed: median 2, 40.7% exactly once, 99.6% at most 1,024 (derived), 978 keys above 1,024 (0.37%, derived; who they are is not measured) with a third of all inputs between them (derived). A 60-block sample of the later era through the explorer, reweighted for the block sample's bias toward frequent signers, puts the median active address at 24 lifetime transactions (an upper bound on signings) and 1.9% above 1,024; 267 addresses, so a rough check, not a scan. Repository `q3/`, aggregates only; the scanner runs on a stopped node's history store in one command, and anyone with a synced node can get the exact later-era figures. So a height of 10 covers nearly every key of the first era, the later era runs heavier, and the roughly thousand heavy keys want height 20 or rotation at the last leaf. Both are wallet settings in the sense that the chain enforces the count whatever the height; no run went above height 4, so the sizes at 10 or 20 are projections.
