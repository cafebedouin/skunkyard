Prepared with Claude Code (Anthropic, Claude Fable 5.1; review seats on Claude Opus 5.5, Grok and Gemini) for cafebedouin using peeryard v0.1.0 (ba56b25) on ergo 6.0.6 (devnet, one mining node), a public ergo 6.0.1 testnet node, sigma-state 6.0.7 for the driver, Fleet for the testnet funding, and a scan of a stopped mainnet node's history store; reviewed in four rounds before posting (`posts/REVIEW-manytime-reply.md`).

A hash-based lock (WOTS, n = 32, w = 16) that one key set spends many times, with the chain refusing any leaf below the key set's index for every box the key set owns, runs on today's node with no fork: on a devnet and on public testnet, as a prototype, not something to use yet. The post's section 5 listed this construction as unimplemented. Details, numbers, limits and one "break it" box follow; nothing is asked of holders or of maintainers.

**The construction.** Two scripts around a state box marked by a token of supply 1, the shape Ergo's oracle pools and the SigmaUSD bank use. The singleton is one box per key set; its script commits to 16 WOTS keys as the AVL digest of their commitments (33 bytes at any count; the count is a script constant too) and carries the key set's index in R4. A spend names a leaf at or above the index, supplies that leaf's signature and lookup proof, and must recreate the singleton with the token and an index above the leaf it used and below the leaf count; on the last leaf the token must instead leave to a script that is neither this one nor the deposit script, at index 0, the intended place being the next key set's singleton. The deposit script, 147 bytes: a box here is spendable only in a transaction whose first output carries the token and has either advanced the index or changed the script against the token-carrying input, which is to say a transaction in which the singleton's script ran. The deposit address is the one a holder gives out; a plain payment to it is a usable deposit, and because the script depends only on the token, the address is the same for every key set that inherits the token (run, not only read: the second key set's deposit address printed identical). The signed message covers every input id, every data-input id (by reading; no data-input case ran) and every output. The verifier is section 2's, reading the commitment from the tree; the index and token checks sit on the left of the `&&` and fail before any hashing.

**Why the deposit rule is phrased that way.** Storage rent lets anyone spend a box that has sat for 1,051,200 blocks by recreating it minus the fee, same script, registers and tokens, and the box's script does not run on that spend (node rule, read, not run). A deposit rule that asked only "is the token among the inputs", which an earlier draft had, would have let a rent collector attach every deposit to a four-year-old singleton's rent spend. Rent collection can neither advance the index nor change the script, so the rule above holds only when the state script ran. What rent still does is strand: a singleton worth less than its fee is collected whole, token included, so the wallet refreshes the singleton within four years. Found by a review seat by reading; it cannot be shown on testnet for about a million blocks.

**Executed, on public testnet** (through a public testnet node, ergo 6.0.1, block version 4; the project's testnet wallet minted the token, then in one transaction funded the singleton, three plain deposits and one plain box at the singleton's own address). Rejected by the node, with script costs in units: a forged signature, 38,018; a spend that does not advance the index, carrying a deposit, 75 (and, evaluated locally, the deposit's own script refuses it at 66); a deposit spent without the singleton, 21; a transaction signed over the singleton alone and posted with a deposit added, 37,864; the plain box at the singleton's address, which has no token, with a valid signature, 23; leaf 0 signed again after the index read 1, 46; the continuing index written as the leaf count, 84; the last leaf with the token kept under the same script, 67; the last leaf with the token sent to the deposit script, 66. Confirmed: leaf 0 sweeping the first deposit (transaction `fba44137…`, index to 1); leaf 3 sweeping the second (`eff260fb…`, index to 4); leaf 15 moving the token to a second key set's singleton at index 0 (`45116cb3…`); that key set's leaf 0 sweeping the third deposit, which had been funded before the rotation (`82bb1a4b…`); the token carried every time, every swept deposit gone from the UTXO set. The devnet (ergo 6.0.6, block version 4) gave the same thirteen verdicts with the same rejection costs except the two that include a hash count.

**The hybrid.** `proveDlog(owner) && (this lock)` ran only under the earlier per-box versions, on the devnet: the hash-only spend without the curve proof rejected, both proofs confirmed, about 200 to 500 units over the plain form in matched rounds and 95 bytes (derived: 56 of proof, 39 of the larger box). Not rerun under this version.

**Numbers, per spend with one deposit** (derived from the printed figures). Script cost 37,930 to 38,187 units on testnet and 37,954 to 38,212 on the devnet for the sweeps, of which the deposit's script is 66; the width is message-dependent and the many-time machinery is not separable from it; the one-time box in section 2 measured 37,592. 3,852 bytes against 2,345: the recreated singleton, 1,312 bytes with its 1,234-byte tree, is an output of every spend, and the deposit is a second input. Per mainnet block about 147 by cost (8,001,091 ÷ (38,212 + 15,708 for two inputs and three outputs + 400, the devnet's measured charge above that formula, by inference token access)) and 329 by size (1,271,009 ÷ 3,852), against 158 (8,001,091 ÷ (37,592 + 13,003)) and 542 for the one-time box on the same measured basis; section 3's 154 used the harness worst case.

**Rent.** The singleton persists, so it owes about 1.64 ERG per four years at the current factor (1,312 bytes × 1,250,000 nanoERG), charged only if it sits unspent that long; its clock restarts whenever the wallet sets the recreated box's creation height to the current one, as this driver does. A deposit is 190 bytes and persists only until swept.

**What the chain enforces** (for the key set, while the token sits in a singleton; executed unless marked). The index never moves backwards and cannot be written past the tree; a leaf below the index cannot spend; a deposit moves only in a transaction where the singleton's script ran and advanced the index or rotated. So a wallet restored from an old backup that signs a leaf the index has passed gets a rejection, for the singleton as run, for a deposit by reading (any failing input fails the transaction). The property this adds over signer-side state, by reading: once a spend with leaf k has confirmed deeply enough to be final, every signature of leaf k is useless, so the forgery window of a doubly signed leaf closes there.

**What it does not enforce.** The chain cannot see a signature that never reaches it. A signer who signs any leaf twice over distinct messages has opened the window: with two signatures a forger can sign some spends of their own at that index, which on an ordinary leaf means the deposits present and on the last leaf means the token as well, and so every future deposit (WOTS property, by reading, not tested). The test procedure itself did this: four leaf-0 signatures and two leaf-15 signatures went to the public node before the corresponding spends confirmed, a race that stayed open until then and that nobody ran; a wallet must never do what the test did. A replacement signed with leaf k + 1 while the original with leaf k then confirms leaves k + 1 disclosed with the index at k + 1, and a wallet rebuilt from the chain that signs k + 1 again has opened the window too. A child transaction pre-signed against the predicted id of an unconfirmed singleton is unsafe for another reason: the transaction id covers context extensions, which a relay can pad, so the id can change under a valid spend (by reading).

**What the wallet must do.** Its counter moves at signing and never decrements; rebuilt from the chain, it would skip ahead past the index by a margin, which the "at or above" rule allows at the cost of the skipped leaves (a rule, not something this driver implements). The token is the key to every deposit: mint exactly one (the supply is public in the mint transaction); refresh the singleton within four years; at the last leaf send the token only to a singleton with the same token id, a root never used before and index 0, since the script forbids only the two worst destinations; never pay the singleton's own address, which is visible on chain, because a payment there without the token is lost; never let a non-Int reach the singleton's R4 (an EIP-4 mint straight into the singleton would; this run minted to a plain box first). Restoring needs the token id, since the singleton's address changes at every rotation while the deposit address does not; the deposit address is a long P2S address, which some services may refuse as a withdrawal target.

**Not shown.** Hiding which leaf signed (the register and the proof name it, so the usage count is public and the token id links key sets across rotations; the proof's sibling hashes reveal nothing about unused leaves' secrets beyond the hash's one-wayness, by reading); domain separation in the chain hashes, absent here as in section 2; adding leaves (the tree is built off chain and read-only); heights above 4, several deposits in one spend, a second rotation, a data-input case, the hybrid under this version (not run); a bad lookup proof at a legal index (by reading, an exception rather than a false); a forged spend still costs the node the full verification and pays no fee, as in the post.

**Break it.** On testnet, key set B's singleton `fbfe80d3…` holds the token `96806629…` at index 1, and a 0.5 ERG deposit, box `f1c89ea6…`, sits at the deposit address (full ids, the address and every transaction above in the repository's result file). A break is a confirmed testnet spend of that deposit, or a transaction the two scripts accept on a devnet or in the harness, carrying no valid signature of an unused leaf of key set B; or an argument that a sentence under "What the chain enforces" is false, which is how the rent finding above was made.

**Prior work.** QRL has enforced one-time use of XMSS indices at consensus since its XMSS addresses (2018 by its documentation): a per-address bitfield over the first 8,192 indices, usable in any order, and above that an ascending counter; this singleton is that counter in UTXO form, with every leaf under the counter, so a skipped leaf is burned. WOTS-Tree (Mateos, ePrint 2026/374) brings XMSS to Bitcoin with up to 2^21 leaves and recovers the index by scanning the chain, the signer enforcing it; Kudinov and Nick (2025/2203) prefer stateless schemes for Bitcoin because of the state-rollback failure, while keeping the stateful option open; BPQS (2018/658) chains two-leaf trees with signer-side state. On account chains, the Solana Winternitz vault (2025) has a program verify one WOTS signature and move the funds to a vault under the next key, and Ethereum contract-wallet proposals keep a stable address while rotating a stored key hash (both from a web search, neither repository read in full). What is added here is a many-time counter enforced by a box script on a UTXO chain under the stock interpreter. The search scope is in the repository's prior-art note; it did not cover the Bitcoin mailing lists, IOTA, or Ergo's own forum and chats for stateful-counter contracts.

**How many leaves.** Under the singleton one signature sweeps any number of deposits, so leaves consumed are transactions signed, plus replacements and skip-ahead margins. Over 791,286 mainnet blocks (789,437 contiguous from genesis plus 1,849 near the tip; by height the 2019 to 2022 era, 42% of today's height, derived), 263,160 P2PK keys signed at least one transaction: median 2, 47.2% exactly once, 99.7% at most 1,024 (derived), 776 keys above 1,024 (0.29%, derived; who they are is not measured) with 27% of all signings between them (derived), the largest below 2^17. A 60-block sample of the later era through the explorer, reweighted for the block sample's bias toward frequent signers, puts the median active address at 24 lifetime transactions (an upper bound on signings, since receipts count) and 1.9% above 1,024, over 263 addresses with a count; a second draw of 40 blocks gave 18 and 2.0%; a few hundred addresses is a small sample. So a height of 10 would cover nearly every key of the first era, height 17 every key in it, the later era runs heavier, and rotation at the last leaf, which this run exercised once, covers the rest. Repository `q3/`, aggregates only; the scanner runs on a stopped node's history store in one command, and anyone with a synced node can get the exact later-era figures.
