Prepared with Claude Code (Anthropic, Claude Fable 5.1; review seats on Claude Opus 5.5, Grok and Gemini) for cafebedouin using peeryard v0.1.0 (ba56b25) on ergo 6.0.6 (devnet, one mining node), a public ergo 6.0.1 testnet node, sigma-state 6.0.7 for the driver, Fleet for the testnet funding, and a scan of a stopped mainnet node's history store; reviewed in three rounds before posting (`posts/REVIEW-manytime-reply.md`).

A hash-based lock (WOTS, n = 32, w = 16) that one key set spends many times, with the chain refusing any leaf below the key set's index for every box the key set owns, runs on today's node with no fork: on a devnet and on public testnet, as a prototype, not something to use yet. The post's section 5 listed this construction as unimplemented. Details, numbers, limits and one "break it" box follow; nothing is asked of holders.

**The construction.** Two scripts, in the pattern Ergo already uses for oracle pools and the SigmaUSD bank: a singleton-token state box. The singleton is one box per key set, marked by a token of supply 1 minted once, whose script commits to 16 WOTS keys as the AVL digest of their commitments (33 bytes at any count; the count is a script constant too) and carries the key set's index in R4. A spend names a leaf at or above the index, supplies that leaf's signature and lookup proof, and must recreate the singleton with the token and an index above the leaf it used and below the leaf count; on the last leaf the token must instead leave to a script that is neither this one nor the deposit script, the intended place being the next key set's singleton. The deposit script, 61 bytes: a box here is spendable only in a transaction that also spends a box carrying the token. The deposit address is the one a holder gives out; a plain payment to it is a usable deposit, and because the script depends only on the token, the address is the same for every key set that inherits the token. The signed message covers every input id, every data-input id and every output. The verifier is section 2's, reading the commitment from the tree; the index and token checks sit on the left of the `&&` and fail before any hashing. Earlier versions kept the index in each box; the review seats found that a fresh deposit then started at 0, and later that the last leaf could hand the token anywhere, which is how the design reached this form.

**Executed, on public testnet** (through a public testnet node, ergo 6.0.1, block version 4; the project's testnet wallet minted the token, then in one transaction funded the singleton, three plain deposits and one plain box at the singleton's own address). Rejected by the node, with script costs in units: a forged signature, 37,918; a spend that does not advance the index, 75; a deposit spent without the singleton, 7; a transaction signed over the singleton alone and posted with a deposit added, 37,948; the plain box at the singleton's address, which has no token, with a valid signature, 23; leaf 0 signed again after the index read 1, 46; the continuing index written as the leaf count, 84; the last leaf with the token kept under the same script, 65; the last leaf with the token sent to the deposit script, 64. Confirmed: leaf 0 sweeping the first deposit (transaction `908e055e…`, index to 1); leaf 3 sweeping the second (`2c3675de…`, index to 4); leaf 15 moving the token to a second key set's singleton at index 0 (`b88aa756…`); that key set's leaf 0 sweeping the third deposit, which had been funded before the rotation (`da38a18b…`); the token carried every time, every swept deposit gone from the UTXO set. The devnet (ergo 6.0.6, block version 4) gave the same thirteen verdicts with the same rejection costs except the two that include a hash count (37,913 and 37,737). The hybrid `proveDlog(owner) && (this lock)` ran only under the earlier per-box versions, on the devnet: the hash-only spend without the curve proof rejected, both proofs confirmed, about 200 to 500 units in matched rounds (derived; message variation of about 150 sits inside that) and 95 bytes (derived: 56 of proof, 39 of the larger box) over the plain form.

**Numbers, per spend with one deposit** (derived from the printed figures). Script cost 37,773 to 37,959 units on testnet and 37,994 to 38,179 on the devnet, of which the deposit's script is 11; the one-time box in section 2 measured 37,592. 3,749 bytes against 2,345, because the recreated singleton, 1,209 bytes with its 1,131-byte tree, is an output of every spend. Per mainnet block about 147 by cost (8,001,091 ÷ (38,179 + 15,708 for two inputs and three outputs + 400, the devnet's measured charge above that formula, by inference token access)) and 339 by size (1,271,009 ÷ 3,749), against 158 and 542 for the one-time box on the same measured basis (section 3's 154 used the harness worst case). Rent: the singleton persists, about 1.51 ERG per four years at the current factor (1,209 bytes × 1,250,000 nanoERG), its clock restarting whenever the wallet sets the recreated box's creation height to the current one, as this driver does; a deposit is 104 bytes and persists only until swept.

**What the chain enforces.** For the key set, while the token sits in a singleton: the index never moves backwards, a leaf below it cannot spend, the index cannot be written past the tree, and nothing at the deposit address moves without the singleton; so a wallet restored from an old backup that signs a leaf the index has passed gets a rejection, for a deposit as for the singleton (executed for the singleton; for a deposit by reading, any failing input fails the transaction). The property this adds over signer-side state: once a spend with leaf k has confirmed, every signature of leaf k is useless, so the forgery window of a doubly signed leaf closes at confirmation. The test procedure itself handed the public node three leaf-0 signatures over distinct messages before the leaf-0 spend confirmed; harmless because nothing spent in that interval, and the index then passed 0.

**What it does not enforce, and what the wallet must do.** The chain cannot see a signature that never reaches it: a signer who signs the current leaf twice off chain, or a replacement signed with leaf k + 1 while the original spend with leaf k then confirms, leaving k + 1 disclosed with the index at k + 1; a wallet rebuilt from the chain that then signs k + 1 again has opened the window. So the wallet's counter moves at signing, never decrements, and a wallet rebuilt from the chain would skip ahead past the index by a margin, which the "at or above" rule allows at the cost of the skipped leaves (a rule, not something this driver implements). The last leaf is the one never to sign twice: two signatures on it let a forger choose where the token goes. The token is the key to every deposit, so: mint exactly one (the supply is public in the mint transaction); keep the singleton's value above its rent fee or spend it within four years, because rent on a box worth less than its fee lets the collector take the box, token included, and with it the deposits (node rule, by reading, not run); at the last leaf send the token only to a singleton compiled with the same token id, since the script forbids only the two worst destinations; never pay the singleton's own address, which is visible on chain, because a payment there without the token is lost; never let a non-Int reach the singleton's R4 (an EIP-4 mint straight into the singleton would; this run minted to a plain box first). Not shown: hiding which leaf signed (the register and the proof name it; the proof's sibling hashes reveal nothing about unused leaves beyond the hash's one-wayness, by reading); heights above 4, several deposits in one spend, a second rotation, the hybrid under this version (not run); a bad lookup proof at a legal index (by reading, an exception rather than a false).

**Break it.** On testnet, key set B's singleton holds the token at index 1 and a 0.5 ERG deposit sits at the deposit address, box `6a09d645…`. Spending that deposit without key set B's next leaf is the challenge; the scripts, keys' public parts and every transaction above are in the repository.

**Prior work.** QRL has enforced one-time use of XMSS indices at consensus since its XMSS addresses (from 2018, by its documentation): a per-address bitfield over the first 8,192 indices, usable in any order, and above that an ascending counter; this singleton is that counter in UTXO form, with every leaf under the counter, so a skipped leaf is burned. WOTS-Tree (Mateos, ePrint 2026/374) brings XMSS to Bitcoin with up to 2^21 leaves and recovers the index by scanning the chain, the signer enforcing it; Kudinov and Nick (2025/2203) prefer stateless schemes for Bitcoin because of the state-rollback failure, while keeping the stateful option open; BPQS (2018/658) chains two-leaf trees with signer-side state. On account chains, the Solana Winternitz vault (2025, a deployed program) verifies one WOTS signature and moves the funds to a vault under the next key, and Ethereum contract-wallet proposals rotate a stored key hash per transaction. What is added here is a many-time counter enforced by a box script on a UTXO chain, with a deposit address that outlives the key set. The search scope is in the repository's prior-art note; it did not cover the Bitcoin mailing lists or IOTA.

**How many leaves.** Under the singleton one signature sweeps any number of deposits, so leaves consumed are transactions signed. Over 791,286 mainnet blocks (789,437 contiguous from genesis plus 1,849 near the tip; by height the 2019 to 2022 era, 42% of today's height, derived), 263,160 P2PK keys signed at least one transaction: median 2, 47.2% exactly once, 99.7% at most 1,024 (derived), 776 keys above 1,024 (0.29%, derived; who they are is not measured) with 27% of all signings between them (derived). A 60-block sample of the later era through the explorer, reweighted for the block sample's bias toward frequent signers, puts the median active address at 24 lifetime transactions (an upper bound on signings) and 1.9% above 1,024, over 263 addresses with a count; a second draw of 40 blocks gave 18 and 2.0%. So a height of 10 would cover nearly every key of the first era, the later era runs heavier, and the few hundred heavy keys would need height 20 or rotation at the last leaf, which this run exercised once. Repository `q3/`, aggregates only; the scanner runs on a stopped node's history store in one command, and anyone with a synced node can get the exact later-era figures.
