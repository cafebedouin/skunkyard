The Standing Rule Analysis (Section 4)\n\nSection 4 defines three forms of output accounting:\n1. *Form 1:* The box is the only input of its script in the transaction (`mine.size == 1`).\n2. *Form 2:* Every input of the script names one output that holds their totals (`next.value \u003e= total - bounty`).\n3. *Form 3:* The output carries the input's box ID (`o.R4 == SELF.id`).\n\n### A. Correctness and Sufficiency\n\n* **Form 1 is NOT sufficient in multi-user or templated contracts.**\n  Form 1 relies on `INPUTS.filter(b =\u003e b.propositionBytes == SELF.propositionBytes).size == 1`. When different users instantiate a template, each user's box has distinct segregated constants and therefore distinct `propositionBytes`. In a single transaction containing Box A (User A) and Box B (User B), both boxes satisfy `mine.size == 1`. If both boxes check that `OUTPUTS(0)` receives value $V$, a single output of value $V$ satisfies both inputs simultaneously, allowing the attacker to steal the remaining value. This was the exact vulnerability demonstrated in [`Pending.es`](file:///tmp/claude-1000/-home-scott-bin-skunkyard/a65732a8-6f71-44fb-a5f0-892e30dc1d10/scratchpad/policy-post-r2-slice/evidence/policy/2-twostep/Pending.es) (row `old-1`). Stating that Form 1 is a valid standing rule without qualification is misleading; Form 1 is safe only when the transaction output is cryptographically bound to the input's specific constants (as in [`Vault.es`](file:///tmp/claude-1000/-home-scott-bin-skunkyard/a65732a8-6f71-44fb-a5f0-892e30dc1d10/scratchpad/policy-post-r2-slice/evidence/policy/2-twostep/Vault.es), where `p.R6 == SELF.propositionBytes`).\n* **Form 3 is the only universally sufficient mechanism for 1-to-1 satisfaction.** Binding the output to `SELF.id` guarantees that an output satisfies exactly one input regardless of script or template overlap.\n\n### B.
