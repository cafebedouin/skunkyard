The Double-Satisfaction Standing Rule (Section 5)\n\nSection 5 of `POST-DRAFT-PROTOCOL.md` presents the three forms of double satisfaction:\n1. **Form 1 (Isolated input):** The box is the only input of its script in the transaction (`mine.size == 1`).\n2. **Form 2 (Consolidated totals):** Every input of the script points to a single output that proves it contains the aggregate totals of all inputs.\n3. **Form 3 (Identity binding):** The completing/cancelling output explicitly embeds the spent input box's unique `boxId` (e.g. in register R4 or R6).\n\n### Sufficiency and Limitations\nSection 5 correctly defines the operational boundary:\n- Forms 1 and 2 count per *script*. They are secure *only* when the output is pinned to that same script.\n- When an output can go to an external or variable script (such as `Pending.es` paying to destination R4), counting per script is insufficient because two different users have different scripts, allowing one output to satisfy two inputs. Form 3 (box ID binding) is required and sufficient to close this cross-contract vulnerability.\n- Section 5 correctly notes two attacks that the rule does *not* cover:\n  1. *Forged input state:* Where an attacker creates a malicious box matching the \"registered\" predicate (resolved by cryptographic registration: welded NFTs or Merkle proofs).\n  2. *Forged data inputs:* Where a contract relies on an external box (such as the QDay flag) found only by token ID, without checking supply or script origin.\n\n### Verification of Cited Theft Rows\nEvery row cited in Section 5 lines 231–247 maps to the exact scenario and form:\n- `two-step row 2b` (REFUSE) vs `results-vault2.json 2b-ng` (ACCEPT): Form 1 vault announce `alone` guard.\n- `two-step row 16` (REFUSE) vs `row 17` (ACCEPT): Form 1 pending cancel `alone` guard.\n- `two-step row 12` (REFUSE) vs `row 14` (ACCEPT): Form 1 pending complete `alone` guard (blocking honest batching row 13; row 15 without guard).\n- `results-crossvault.json old-1` (ACCEPT) vs `new-1` (REFUSE), and `results-vault2.json v-10`, `v-7c`, `v-7d` (all REFUSE): Form 3 box ID binding on completion and cancellation.\n- `keepalive/devnet-results.json case 9` (REFUSE): Form 3 box ID binding on lone refresh in `KeepAlive.es`.\n- `address-results.json case 6` (REFUSE): Form 2 enforcement (disallowing splitting across multiple outputs).\n- `6-rekey/results.json row 13d` (REFUSE): Form 2 enforcement (requiring exactly one registered input per merge).\n\n---\n\n## 5.
