## SLH-DSA

For SLH-DSA-SHA2-128s the script is the same predicate as FIPS on a 32-byte message and an empty context: length 7,856, `M' = 0x00 ‖ 0x00 ‖ M`, MGF1-SHA-256 with a four-byte counter 0 truncated to 30 bytes, 21-byte FORS message, `idx_tree` the next 7 bytes mod 2^54, `idx_leaf` the next 2 bytes mod 2^9, FORS (k=14, a=12), seven XMSS layers (h'=9, WOTS+ len=35, w=16), SHA2-128 simple tweak `Trunc_16(SHA-256(PK.seed ‖ 48 zero bytes ‖ ADRS_c ‖ M))`, root compared to `PK.root`. Parameter set and address layout match Table 2 and the compressed ADRS in §11.2. I checked the literals `18014398509481984` (2^54), `512` (2^9), `4096` (2^12), `704`, `2928`, `560`, `208`, `12884901888` (type 3), `17179869184` (type 4), and `4294967296` (type 1) against those sizes. The WOTS checksum at lines 71–75 does not write the FIPS left shift by 4. For `lg_w = 4` and `len2 = 3` the three digits `(cSum/256, (cSum/16)%16, cSum%16)` are the same integers as that shift. A later edit that adds the shift on top of this formula will reject honest signatures.

Checks more than the standard:

- Lines 24–26 fix `M` as `0x00 ‖ 0x00 ‖ blake2b256(SELF.id ++ OUTPUTS.bytesWithoutRef)`. A FIPS-valid signature with a non-empty context, a pre-hash `M'` (leading `0x01`), or any other message is rejected. No theft input. A wallet that signs a different framing locks the box.
- Lines 18–19 and 102 fix the public key as compile-time constants. Another key's valid signature is rejected. The devnet row "another key" and the harness negative `other_key_same_digest` record that refusal.

Checks less than the standard: none that accept a signature FIPS rejects, for this parameter set and this `M'`. Algorithm 20's only explicit reject, besides the root comparison, is the length. Line 102 has it. Appended bytes still recompute the same root from the first 7,856 bytes; the size test is what returns false. That is the hole the unguarded sibling in `slhdsa/README.md` demonstrated, and the guard closes it. Truncation either skips `fin` or fails the slice. Both reject the spend. The harness cost 328 and the node cost 150 (`slhdsa/README.md`) show sigma-state 6.0.7 and node 6.0.7 take the short-circuit path.

Depends on the harness or the chain, not on literals in `SlhDsa.es`:

## WOTS+

Same construction for the vault. `WotsPlus.es` and `wotsplus.ts` with an empty prefix implement one scheme: n=32, w=16, 64 message nibbles, checksum `Σ (15 − digit)`, three base-16 digits, 67 chains, `T = blake2b256(seed ‖ [c, s] ‖ x)`, commitment `blake2b256(seed ‖ pk_0 ‖ … ‖ pk_66)`, signature element = chain value at step `digit`, verifier hashes steps `digit .. 14`. Keygen hashes steps `0 .. 14` (`wotsplus.ts` lines 16–19 and 48, `WotsPlus.es` lines 37–38). `QVault.es` lines 33–55 are the same checker plus `mine.size == 1`. The 48 script accepts in `pqwallet/RESULT.md` are the empirical check that Ergo's `blake2b256` matches `@noble/hashes` blake2b-256 with no key and no personalization (`bytes.ts` lines 8–9). I did not inspect the noble implementation.

The schedule is a different tweak. `keygen(..., prefix)` inserts `prefix` between the seed and `[c, s]` (`wotsplus.ts` line 18). `scheduleKeys` passes the leaf index (`derive.ts` line 120). `WotsPlus.es` has no prefix byte. A schedule signature will not verify under `WotsPlus.es`. `RekeySchedule.es` is not in this directory, so I did not check that contract.

Sound as a one-time signature, under blake2b-256 being one-way. The digit map on a 32-byte digest is bijective, and the checksum max is 960, which fits in three base-16 digits (below 4096), so the encoding is injective. Hashing a chain forward only raises that chain's digit. A second message would need every digit, checksum included, at least the signed digit. Componentwise that forces the checksum integer up, while a larger message-digit sum forces it down, so only the original digest works. One signature cannot be turned into a signature for another message. Grinding outputs does not get there either: there is no other 32-byte digest in the dominating set.

Two signatures can. For each chain the attacker keeps the earlier of the two revealed values and can sign any digest whose digits all sit at or above that minimum. For typical distinct pairs that set contains other messages. `WotsPlus.es` will verify each of those. The script has no single-use state. `QVault.es` line 32 blocks two boxes of the vault in one transaction and does not block a later box. README row m3 records the node's verdict: after the hash-key spend, a merged late payment is spent by a second signature under the same key.

This is not RFC 8391 and not the FIPS 205 WOTS inside SLH-DSA. Security is the checksum argument above, plus a fresh 32-byte public seed so `(seed, c, s)` does not collide across vaults. Reusing a seed across commitments brings the multi-target search back. The script will not notice. `derive.ts` lines 97–100 use a different seed leaf per vault index.

## Derivation

The BIP32 inversion is correct. `siblingFromXpub` (`derive.ts` lines 145–151) is `k_parent = k_i − IL_i (mod n)` with `IL_i = HMAC-SHA512(chainCode, compressedPublic ‖ ser32(i))`. That is the non-hardened step. The author's test line says the depth-4 xpub at `m/44'/429'/0'/0` plus child 0's private key reproduces child 7. I did not re-run it. From that parent key and the xpub's chain code, every sibling and every hardened descendant of those siblings follows. A quantum adversary gets one child private key because an Ergo P2PK address reveals the public key. Hardened steps above the exported node are not inverted by this: `IL` for a hardened child is `HMAC(chainCode, 0x00 ‖ parentPrivate ‖ index)`, which needs the parent private key.

The sentence "EIP-3 names the depth-4 node" is the author's claim. The EIP text is not in this slice, and I did not fetch it. The path shape `m/44'/429'/account'/change/index` with the last two levels non-hardened matches EIP-3 as I know it. If a wallet instead exports the account xpub at depth 3, the same inversion yields the account private key, and a hardened child of the account is exposed too. Option A still sits above that fork. The test that would lock the claim, recovering an option-A or option-B leaf from the EIP-3 xpub, is not in `derive.test.ts`.

Option A (`derive.ts` lines 49–57, path `m/8391'/429'/account'/scheme'/use'/index'`, every level hardened) is not reached from the depth-4 xpub, and not from the account xpub. The leaf is a secp256k1 scalar. The mod-n bias against a uniform 256-bit string is about 2^−128, which is not the problem. The problem is that the scalar is a real secp256k1 private key. Shor's algorithm on the leaf public key, or on an ancestor public key together with that node's chain code, returns the post-quantum secret. `@scure/bip32` will compute that public key whenever something reads `.publicKey` or an xpub on that branch. The master xpub is enough: Shor recovers the master scalar, the xpub holds the master chain code, and hardened derivation then walks `8391'`. Option A stays post-quantum only while every public key and xpub on that branch, including the master, is never exported. The code does not enforce that.

Option B (`derive.ts` lines 61–80) is sound for a wallet. The root is `HMAC-SHA512("ergo-pq/v1", BIP39 seed)`, and each child is the SLIP-0010 hardened step with no scalar add: `HMAC-SHA512(chainCode, 0x00 ‖ key ‖ ser32(i + 2^31))`, key and chain code replaced by the two halves. Leaves export the 32-byte key and drop the chain code, so one leaf does not open siblings. There is no curve point. The BIP32 master key is `HMAC-SHA512("Bitcoin seed", seed)` and does not reveal the seed, so a master-xpub break does not reach B. Public seed and WOTS secret are different leaves (lines 97–100), so publishing the seed in the script does not publish the secret. Option C is B on a second mnemonic: same cryptography, a second phrase to lose.

Use B. Keep A only as a device-internal path on hardware that already implements BIP32 and will not serialize a public key for that branch. The purpose number 8391 and the domain string `ergo-pq/v1` still have to be fixed before a second wallet writes the same bytes. That is an interoperability requirement, not a break.
