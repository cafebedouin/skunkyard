2. **[ERROR]**
   > *"The test procedure itself handed the public node three leaf-0 signatures over distinct messages before the leaf-0 spend confirmed; harmless because nothing spent in that interval, and the index then passed 0."*
   
   A cryptographer would object strongly to characterizing the exposure of multiple WOTS signatures for the same leaf as *"harmless because nothing spent in that interval"*. In Winternitz one-time signature schemes, exposing two or more distinct signatures under the same key component completely breaks existential unforgeability. In an adversarial blockchain environment, any observer or miner in the P2P mempool could have constructed a forged WOTS signature on a predatory transaction (e.g. sweeping deposits to an attacker's address or redirecting the singleton token) and front-run the valid spend. It was harmless solely due to the benign, low-activity conditions of the testnet run, not due to any cryptographic or protocol protection. This sentence should be revised to acknowledge that exposing multiple unconfirmed signatures of a leaf is fatal in an adversarial setting.

3. **[SUGGESTION]**
   > *"The last leaf is the one never to sign twice: two signatures on it let a forger choose where the token goes."*
   
   Stating that the last leaf is *"the one never to sign twice"* implies that intermediate leaves can tolerate double-signing. This is false: double-signing *any* leaf before confirmation allows an attacker to forge transactions at that index, redirect outputs, and steal funds/deposits being swept. What is unique about the last leaf ($leaf = leaves - 1$) in [`state.es`](file:///tmp/claude-1000/-home-scott-bin-skunkyard/75b0b235-829f-46eb-8d04-11e83d2a336f/scratchpad/reply-slice6/state.es#L25-L27) is that the script permits the singleton token to exit to an arbitrary external script (other than `SELF` or `depositTree`), meaning a forgery on the last leaf allows permanent hijacking of the singleton token itself. Suggest rewording to clarify that *no* leaf may be signed twice, and that the last leaf carries the additional catastrophic consequence of arbitrary token reassignment.

4. **[SUGGESTION]**
   > *"The property this adds over signer-side state: once a spend with leaf k has confirmed, every signature of leaf k is useless, so the forgery window of a doubly signed leaf closes at confirmation."*
   
   A cryptographer would note that closing the forgery window at confirmation assumes finality. On a Proof-of-Work chain like Ergo, re-organizations occur. If a block confirming leaf $k$ is reorganized out, the UTXO state reverts, the on-chain index rolls back to $k$, and any previously disclosed conflicting signatures for leaf $k$ become immediately exploitable by an adversary or miner. Suggest qualifying that this window closes only upon reaching sufficient confirmation depth (settlement finality).

5. **[SUGGESTION]**

However, a malformed lookup proof at a legal index executes `root.get(...).get`, which throws an unhandled exception (`NoSuchElementException`). A blockchain engineer would note that verifiers should ideally be total functions returning boolean `false`; failing by unhandled exception bypasses standard script cost deduction and can create mempool evaluation asymmetries.
