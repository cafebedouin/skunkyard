# Prompt for the ergo_logic / peeryard instance: register skunkyard's node-layer foundations

Paste to the instance working in `~/bin/ergo_logic` (whose register is `issues.json` -> `ISSUES.md`, generated by
`python/gen_issues.py`). Written 2026-10-02.

---

skunkyard (the research repository at ~/bin/skunkyard, public at https://github.com/cafebedouin/skunkyard) has sorted
its worklist by the layer that settles each question. Its `script`, `chain` and `tooling` items are settled by a
single node's answer, a chain scan or an SDK, and stay there. Its `node` items are settled only by a network under
load, an adversary or a version comparison, which is peeryard's instrument, so they belong in ergo_logic's register
and skunkyard consumes the result. Please register the eight foundations below as program items (`P-` ids, or the
`E-` subject where the foundation is a property of the ergo node rather than of the apparatus; your call), lane
`later` unless one is already covered by an existing scenario, and report back the ids you assigned so
`~/bin/skunkyard/WORKLIST.md` (section "Foundations") can link them. Register only; run nothing and post nothing.
Each entry's `detail` should name the origin as "skunkyard WORKLIST F<n>, assumed by SK-<ids>"; `next_action` is
the scenario to write in the `diffrun/scenarios/lib/rig-scenario.sh` style unless an existing scenario already
answers it, in which case name that scenario and mark the foundation measured.

The eight foundations, with what skunkyard already has:

- **F1 Storage rent collection as an actor.** What a box looks like after one collection: guard not evaluated,
  registers kept, `creationHeight` reset, value reduced by the fee, a box below the fee consumed. Needed per deployed
  contract type: a WOTS-locked box (`q2/wots-constant.es`), a Basis reserve (BetterMoneyLabs/basis-tracker
  `contract/basis.es`), a TSNP note (spec in `tsnp/tsnp-spec-v0.6.md`), an agent policy box (to be written).
  Assumed by SK-005, SK-006, SK-008, SK-019, SK-021. Status: read from docs and the rent code only. Scenario shape:
  a devnet with the rent age shortened by config if the node allows it, boxes of each type created, then the miner's
  rent transaction, then a spend attempt of the recreated box; print the box before and after and the spend verdict.
- **F2 Clock bounds.** The consensus rule on the pre-header timestamp (how far ahead or behind a miner may set it),
  `HEIGHT` monotonicity, how `creationHeight` is validated against the block height, and whether any of these can
  be pushed by a mining node under the rig's control. Assumed by SK-019 (Basis compares issuer-set millisecond
  timestamps) and SK-022. Status: read; not executed.
- **F3 Mempool and candidate policy.** Which outputs the candidate builder counts as a fee (skunkyard's reading of
  `ErgoTreePredef.feeProposition` says only the standard fee script's bytes; a fee output locked to one miner's key
  would then count as no fee); ordering by fee rate; the minimum fee; cleanup of transactions whose scripts become
  invalid with height (`CleanupWorker`); chained unconfirmed spends; whether a second transaction can replace one the
  node rejected. Assumed by SK-005, SK-007, SK-008, SK-009 (its questions I1 to I3 are exactly this), SK-017, SK-019
  (tracker reordering). Status: `txload` and `txchain` cover chained spends; fee recognition and height-dependent
  cleanup are not covered. Scenario shape for I1: two mining nodes A and B; a transaction whose fee output is
  `proveDlog(A) && HEIGHT > created + delay` instead of the standard fee script; observe which miner includes it,
  what `/transactions/unconfirmed` says, and whether a stock node counts its fee at all.
- **F4 Input-block ordering at block version 4.** Which input block a transaction lands in; what "before" means for
  a chained pair (B spends A's output) and for an independent pair; whether anything a transaction carries moves it
  earlier. Assumed by SK-009 (I3) and by the forum post's statement that sub-blocks shrink the mempool window.
  Status: the matrix scenarios exist; none asks the ordering question.
- **F5 Parameter voting mechanics.** On a devnet, how many epochs of sustained voting move `maxBlockCost` or
  `maxBlockSize` by a given factor at the `currentValue / 100` step, and the sub-block parameter (id 9). Assumed by
  the forum post's claim that miner votes close the post-quantum capacity gap (SK-001) and by SK-023, whose chain
  half (reconstructing mainnet's vote history from block extensions) skunkyard keeps. Status: read from
  `Parameters.scala`; not executed.
- **F6 Script cost accounting at the node.** Executed by skunkyard (the 12,200 residual on every devnet run,
  `q2/RESULT.md`). No scenario needed; listed so the register knows it is measured.
- **F7 Indexer and explorer behavior.** Tooling, skunkyard's (SK-020); listed for completeness. The node-side part,
  what `extraIndex` adds and costs, is yours if you want it.
- **F8 Relay of large or unusual transactions.** The 2,345-byte WOTS spend and 4 KB boxes against the 96 KB relay
  cap and fee-per-byte ranking across several nodes; ergo_logic's E-066 (fee-per-byte denominator) is adjacent.
  Assumed by SK-001's capacity figures. Status: single-node devnet and testnet acceptance observed; relay across
  peers not measured.

Evidence skunkyard can hand over for any of these: the devnet hooks under `q2/devnet/` and `skunks/oneshot/devnet/`
(rig-style, already run under `review/with-lock.sh`), the cost harness `q2/run.sh`, and the scanner `q1/`. The
person who runs both repositories asked for this registration; the skunkyard items that depend on a foundation
will not be scheduled before its ergo_logic item has a measured answer.
