The revenue ordering and the default-off switch are wired so that a stock config, and a failed or oversized mempool read, stay on the configured share, and the candidate builder's package pass still caps the admitted package at `blockShare` of the block. The safety claim does not hold for the share this PR actually grants: the grown allowance is the package budget minus the measured demand, other sources are added on top of that, and a successful but short or under-measured mempool read is treated as the whole demand. ## Defects

**1. The grown share can push a waiting mempool transaction out of the block.** `Upkeep.opportunistic` (`new/app/transactions/upkeep/Upkeep.scala:220-225`) sets the share to `pkg.less(demand)`, where `pkg` is `CandidateBudget.of(blockSize, blockCost, blockShare)` (`UpkeepSource.scala:313`). That remainder is only the client's package share. `CandidateBuilder` then admits every source, upkeep last (`new/app/tasks/StartMiningServer.scala:153-158`), against that same package budget after genesis (`context/app/mining/CandidateBuilder.scala:557-564`). The per-source pass cannot trim it: `UpkeepConfig.allowance` (`new/app/configs/UpkeepConfig.scala:63-66`) sets this source's byte and cost limits to `Long.MaxValue`, and the builder applies those limits at `CandidateBuilder.scala:493-494`. The node still adds its own transactions and a remainder this client does not choose (`new/conf/application.conf:178-181`, `context/app/transactions/candidate/CandidateBundle.scala:32-37`). I infer from those comments that miner transactions and mempool transactions are additive against the block; the node source is not in this slice.

Concrete input, all inside the supported range (`application.conf:181-182` recommends keeping `blockShare` below 0.8; default upkeep `maxBytes` is not required for the arithmetic): block 1,000,000 bytes, `blockShare` 0.8 so the package is 800,000, other sources 250,000, configured upkeep 50,000, mempool demand 300,000. The remainder is 500,000, which is above the configured share, so upkeep takes 500,000. The package pass admits 250,000 + 500,000 = 750,000, under the package cap. Package plus the measured mempool is 1,050,000, so 50,000 bytes of transactions that were already waiting do not fit. With the configured share left alone, the package would have been 300,000 and those transactions would have fit. The same relation holds for cost.

At the default `blockShare` of 0.5, with demand not understated, this inequality does not arise: growth only happens when demand is below the package, and the complement of a half-block package is at least that large. Verified by the formulas above. The code never checks `demand <= block - package`.

Fix: grow only when the measured demand still fits beside a full package (`demandBytes <= blockBytes - pkg.maxBytes` and the same for cost), and keep the configured share otherwise. Cap the allowance passed to the builder at that package budget. `Long.MaxValue` is wider than the block, so the per-source pass cannot be the backstop.

**2. A successful but incomplete mempool read is treated as full demand.** `Upkeep.demand` (`Upkeep.scala:182-198`) ends the scan when a page is shorter than 100 (`line 192`) and returns whatever it summed. A page that throws fails the surrounding `Try`, and `UpkeepSource.opportunisticShare` (`UpkeepSource.scala:314-316`) keeps the configured share. A `Success` that is merely short does not. I could not find the node client's page cap in this slice, so I cannot show that a live node returns a short page while more transactions exist. The control flow is there if it does.

`Upkeep.weight` (`Upkeep.scala:206-208`) trusts `tx.size` and, when `cost` is absent, charges `bytes * maxBlockCost / maxBlockSize`. That is the block's average density, not an upper bound: a small, script-heavy transaction is counted cheap, `left.maxCost` stays large, and the share grows on a dimension the mempool still needs. The comment at `Upkeep.scala:171-173` says counting every waiting transaction can only overstate demand. That is false for this fallback. Missing `size` uses `NodeCodecs.encodeTransaction(tx).toString.length`, the same fallback `CandidateTx.ancestor` already uses (`context/app/transactions/candidate/BlockTxMessages.scala:51-54`). If that string is longer than the consensus size, bytes are overstated, which keeps upkeep smaller. I could not see `encodeTransaction` in this slice.

Fix: if `size` or `cost` is missing, fail the read and keep the configured share. Keep failing the whole read when any page throws.

**3. A strictly cheaper due box can wait forever, and heartbeat changes order with no new setting.** `advance` rotates by height, then `Upkeep.byWorth` sorts by revenue per byte, then per cost (`UpkeepSource.scala:237-239`, `Upkeep.scala:84-86`). The sort keeps the rotated order only among equal keys. The test at `new/test/transactions/upkeep/UpkeepSpec.scala:172-178` locks that for one input. Stability of `sortBy` generally is the Scala 2.12 library sort; I did not find that implementation in the slice. The old build order was the rotation alone, so that a box stuck at the head could not starve the rest (`context/app/transactions/upkeep/UpkeepSource.scala:196-198`). The new comment (`UpkeepSource.scala:205-207`) still says the rotation does that. It does so only inside one worth.

Input: heartbeat period 1, more due boxes than slots, distinct R6 tips. `HeartbeatJob.expectedRevenue` (`new/app/transactions/upkeep/jobs/HeartbeatJob.scala:51`) is the tip whenever that job is enabled. It is not behind `space`. The highest tips fill every block, and a lower tip never advances. Any job that leaves `expectedRevenue` at 0 (`UpkeepJob.scala:54`) sits behind every positive tip the same way.

`HeartbeatJob.scala:46-49` says a box ranked on a tip it cannot pay costs one build, not a share slot. `plan` still returns a successor when the box pays nothing (`HeartbeatJob.scala:57-61`), and `attempt` admits any successor that fits (`UpkeepSource.scala:355-362`). The slot is spent.

With heartbeat left disabled, which is how `application.conf` ships, every box reports 0 and the rotated id order is unchanged. Verified: equal worths, stable order, and the rotation spec at `UpkeepSourceSpec.scala:498-511` sets no tips.

Fix: age a box that has been deferred, or keep the height rotation as the order and use worth only to break ties inside the slots that will actually be built. Report the tip `plan` will pay, including 0 when the beat is free.

**4. A wrapped cost sum inflates the share past the package budget.** `demand` adds reported costs with `+=` (`Upkeep.scala:188-191`). `cost` is a `Long`; the source spec's crowd transaction uses `Long.MaxValue / 4` (`UpkeepSourceSpec.scala:559-560`). Two such values wrap negative. `CandidateBudget.less` (`CandidateBundle.scala:41-42`) then does `max(0, package - negative)`, which is larger than the package, and `opportunistic` adopts it. The package pass trims admission back to the package budget when `readBudgets` succeeds (`CandidateBuilder.scala:561-564`). When that read fails the budgets are `Unbounded` (`CandidateBuilder.scala:638-640`), and the inflated share is not trimmed. Real Ergo costs are far below this; it wants a saturating add or a failed read on a negative total.

Checked, no concern:

- The multiply in `weight`. `maxBlockSize` and `maxBlockCost` are `Int` (`context/app/transactions/rent/RentVerifier.scala:94-99`), and the tests pass `size` as `Int`. `Int.MaxValue * Int.MaxValue` fits in a `Long`. The divisor is at least 1. Truncation is less than one cost unit.
- Worth arithmetic. Revenue and the floor are `Long`s turned into `Double`; there is no integer division and no divide-by-zero (`Upkeep.scala:69-70`). Values above 2^53 lose integer precision. A heartbeat tip in that range is not a case this job produces.
- A page that throws. The whole `Try` fails, including a failure after a successful earlier page, and the configured share stands. The scan also stops once either dimension has reached the package budget, and a mempool deeper than 20 pages is charged as that whole budget (`Upkeep.scala:183-185`). Both keep the configured share.
- What pending transactions do. `weight` reads `size`, `cost`, and, only when `size` is absent, the encoded length. It does not branch on inputs, outputs, or scripts.
- The cost of the read, when the mode is on. At most 20 sequential pages of 100 full transactions, inside the build's `getClient.execute`, with an early stop once demand fills either side of the package budget. Fixed mode never calls it (`UpkeepSource.scala:227`). Default source deadline is `blockTxTimeout` minus at most 2 seconds (`CandidateBuilder.scala:45-46`), which is about 18 seconds at the default 20-second timeout. Twenty local node calls fit in that. A pathologically slow node can still make this source miss the deadline and contribute nothing; that is the existing deadline, not a new loop.

A bug that kept the sum of earlier successful pages and returned `Success` would still pass. The name describes the second case.

`UpkeepSourceSpec` "grow into an empty mempool's remainder, up to opportunisticMaxTxs" (`UpkeepSourceSpec.scala:562-567`) asserts three bundles. Configured `maxTxs` is 1 and the cap is 3, so any growth to three slots passes. It never checks that the byte and cost share equal the package remainder. The fixture's `blockShare` is 1.0 (`UpkeepSourceSpec.scala:80`), so an empty mempool's remainder is the whole block.

The most important missing test is the composition in defect 1: `blockShare` 0.8, other sources holding part of the package, mempool demand between `block - package` and `package - configured`, then the admitted package plus that demand compared with the block limit. Nothing here drives `CandidateBuilder`. Next is `demand` with one successful page and a thrown second page, expecting `Failure`.

## Design

Compute one room figure and hand that to the builder: block limits, `blockShare`, genesis, and mempool demand, growing only when demand fits in the complement of a full package. Delete the `Long.MaxValue` allowance. The source and the builder currently each invent a budget, and only the later one knows about genesis and the other sources.

Rank inside the existing height rotation, and make heartbeat report the tip `plan` will actually pay. A total order on an upper bound, with no age, fights the liveness the rotation was added for.

When `size` or `cost` is absent, fail the read. An estimate that is not an upper bound is the wrong direction for a path whose invariant is "understated demand takes someone else's space."

## PR description

The description is right that the mode defaults to fixed, that equal worths keep the old rotation, that a thrown read, a full mempool, and a mempool deeper than 20 pages keep the configured share, that the builder bounds sources again, and that this path counts pending transactions instead of interpreting them. `weight` (`Upkeep.scala:206-208`) matches that last claim.

Three claims are wrong. "With an unchanged config, behaviour is the same as the upkeep PR's" is false once heartbeat is enabled: `expectedRevenue` reorders due boxes in fixed mode too. It is true while heartbeat stays off. "Never past opportunisticMaxTxs" is false when configured `maxTxs` is higher; the code uses `max(configured.slots, maxTxs)` (`Upkeep.scala:224`), and `UpkeepSpec.scala:198-199` requires the configured count to win. "Takes space that no transaction waiting now wants" and "never more than the remainder" describe the package remainder, not the block after the other sources. The policy question asks only whether fee-less work may take space a transaction might want later, while the block is mined. That future race is real, and leaving the mode off by default is a fair way to pose it. It is posed as if transactions already in the mempool were protected. Defects 1 and 2 say they are not, for `blockShare` above one half and for a short or under-measured read. The maintainer is being asked to accept a narrower risk than the code has.

`application.conf:277-278` says the read is of the fee-paying transactions waiting. The code sums every unconfirmed transaction, fee or not (`Upkeep.scala:188-191`). Counting fee-less mempool transactions too only makes upkeep smaller.
