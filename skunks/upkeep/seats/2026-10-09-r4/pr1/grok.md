## Defects

### 1. Exhausted boxes fill `maxBoxesPerJob` and payable boxes past them are never tracked

`UpkeepSource.scala:395-400` keeps every configured id and then `rest.take(maxBoxesPerJob)`. `rest` is discovery order. For heartbeat that is due-height ascending (`ScriptJob.scala:118`, `HeartbeatJob.scala:53`). `offered` is that set minus `memory.heldIds` (`UpkeepSource.scala:165-170`), and held includes exhausted ids (`UpkeepSource.scala:465`). A box heartbeat still `maintains` (`HeartbeatJob.scala:48`, `tip >= minTip`) but whose `plan` returns `None` (`HeartbeatJob.scala:59-68`) is marked exhausted (`UpkeepSource.scala:344-351`) and stays exhausted until a scan stops finding it (`UpkeepSource.scala:487-492`).

That happens for a box whose value is below the successor floor, and for any box when `minTip > 0` if the tip it offers cannot fund its own output. The second case is cheap: the script is public, `lastBeat = 0` and `period = 1` sort first, and a box can advertise `tip >= minTip` while holding only about one consensus minimum. The first `maxBoxesPerJob` of those (default 256, validation max 4096) occupy the cap forever. A payable box later in the same 1,000-box index window is cut by `take` and never offered. Configured `boxIds` are outside the `take`, so a pinned id still works. Refused ids do the same while they sit out `retryAfterScans`, then get one more build; exhausted ids do not return.

Fix: drop ids already in `memory.exhaustedIds` out of `rest` before `take`. Still pass every id this scan found into `memory.passed`. `passed` intersects the exhausted set with `known` (`UpkeepSource.scala:491-492`). If those ids are removed from `tracked` and `known` is only `tracked` (`UpkeepSource.scala:105-106`), the hold is forgotten and the same boxes win the cap again next pass.

### 2. A discovered input that this build did not read back skips both safety checks

`walletInputs` (`Upkeep.scala:95-96`) flags an input only when `treeOf.get(id).exists(wallet.contains)`. A missing tree is treated as not a wallet box. `undiscoveredInputs` (`Upkeep.scala:86-87`) is `spentIds -- discovered`. The build passes the whole tracked set as `discovered`, including held ids (`UpkeepSource.scala:168-170`, `353`). `treeOf` is built only from this build's read-back of `offered` (`UpkeepSource.scala:212-221`). The comment at `Upkeep.scala:93-94` says an unread input is caught by `undiscoveredInputs`. That is true only when the unread id is absent from `discovered`.

State that gets through: `discover` has returned wallet id `W` and box `G`. A previous build read `W` back, the job kept the bytes, and the source refused that spend, so `W` is held. The next build offers only `G`. `build(G)` spends `W` and `G`. `W` is still in `discovered`, so it is not foreign, and it is not in `treeOf`, so it is not a wallet hit. The successor is admitted (`UpkeepSource.scala:355-362`). `UpkeepSourceSpec.scala:371-378` only puts the wallet box alone in `discovered` and in the live read-back, so this path is the one the spec covers.

Verified for the shipped job: `ScriptJob.discover` keeps a box only when `ergoTree` is the job's tree and EIP-27 does not block it (`ScriptJob.scala:105-109`). `signed` calls `setInputs(box)` and `newProverBuilder().build().sign` (`ScriptJob.scala:166-172`). `build` is `final` (`ScriptJob.scala:122`). The only factory is `HeartbeatJob.Factory` (`UpkeepRegistry.scala:30`). A P2PK wallet box is not that tree, and the empty prover cannot sign it. Inferred: a later `UpkeepJob` that closes over a prover with keys, which `BuildContext` does not hand out (`UpkeepJob.scala:76-81`), can do this. The trait is the extension point the description names for a job that spends more than one box (`UpkeepJob.scala:14-20`, `ScriptJob.scala:55-56`).

Fix: refuse unless every spent id is a key of `treeOf`. Then apply the wallet-tree test. Presence in `discovered` is not enough.

## Tests

`DueJobSpec.scala:145-154`, "a box whose R4 + R5 passes Int.MaxValue is not due", only asserts `rejectsAtSigning`. The comment on the property says an `Int` overflow would also fail the script, so the test does not show the header's claim that the sum is taken in `Long` (`DueJob.ergo:9-11`).

`DueJobSpec.scala:190-200`, "all but a box's minimum may be taken", keeps `Parameters.MinChangeValue` and calls `accepts`, which is `prover.sign` (`ContractSpecBase.scala:134-139`). That shows the script allows a successor of `MinChangeValue`. It does not show the consensus per-byte minimum, and `prover.sign` does not check that rule.

`UpkeepSourceSpec.scala:172-178`, "The wiring should start a source only when it is enabled and config turns on a job", asserts `UpkeepSource.runs` only. It does not start `StartMiningServer`.

The most important missing test: with `maxBoxesPerJob = N`, `N` boxes that `maintains` and whose `plan` returns `None`, plus one payable box later in discovery order, the payable box is still offered on the next build. The regression the wallet fix needs, which the current wallet spec does not cover: discover `W` and `G`, refuse a build that spends `W`, then refuse a later build of `G` whose transaction also spends the remembered `W`.

## Design

Make "read back this build" the single input guard, then the wallet-tree test, and drop the split between `discovered` and `treeOf`. Apply the per-job cap after removing exhausted ids, and feed the full found set to `memory.passed` so the hold survives. Leave the 1,000-box index window as the documented bound it already is. Confirm, in a test that builds the real heartbeat transaction, that `Eip27Adjustment.adjust` does not append an output when the fee is 0 and the burn is empty. Treat a `/transactions/check` refusal that is not "wrong height" as worth remembering; with the default on, a check that rejects every height-pinned beat offers nothing and retries forever.
